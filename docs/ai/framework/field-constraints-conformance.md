# Field constraints: the conformance corpus

A field's constraints are declared once and evaluated **twice** — by
`FieldConstraintsEnforcer` on write, and by whatever renders the form, against the values the user
is typing. The feature only works if the two agree. They did not: a cross-implementation audit of the
first frontend found **seven** places where the same declaration and the same row produced opposite
answers, and three rounds of review found fifteen defects in that evaluator, every one of them a
sentence of the contract read differently.

Prose cannot hold that line. A reader implements what they understood, and nothing fails until a user
meets it. This document specifies a **corpus**: a data file of `(declaration, row, expected)` rows,
generated from the real evaluator, that any second implementation runs as a test.

`FilterEvaluator` is the authority. Where this document and that class disagree, the class is right
and this document is stale.

## The file

```json
[
  { "case": "null and empty text are one value",
    "condition": "reason = \"\"",
    "fieldTypes": { "reason": "Option" },
    "row": { "reason": null },
    "expected": true }
]
```

`condition` is the expression spelling; `fieldTypes` gives the **declared** type of every field the
case names, because the type decides the comparison; `row` is the raw row as a write would carry it;
`expected` is what the evaluator answered.

Generated by a test in `softa-orm` that runs every case through `FilterEvaluator` and fails if the
file disagrees — so `expected` is never hand-written and cannot drift from the code. A client
implementation reads the same file and asserts its own answers match.

## What the corpus covers

### Emptiness

`null`, `""`, a missing key and an empty collection are one value: "nothing there".

| Condition | Row | Expected |
|---|---|---|
| `reason = ""` | `{reason: null}` | true |
| `reason = ""` | `{}` | true |
| `country != ""` | `{country: null}` | **false** |
| `tags = ""` (MultiOption) | `{tags: []}` | true |
| `tags IS SET` | `{tags: []}` | **false** |
| `tags IS NOT SET` | `{tags: []}` | true |

The `!=` row is the one that catches a naive implementation: two empties are *equal*, so their
inequality is false. An implementation that tests `left === right` on `null` vs `""` answers the
opposite.

### Ordering needs two values

`<`, `<=`, `>`, `>=` and `BETWEEN` are false when either side is empty; a negation answers the
opposite of what it negates.

| Condition | Row | Expected |
|---|---|---|
| `endDate < "{{ @startDate }}"` | `{}` | false |
| `endDate < "{{ @startDate }}"` | `{startDate: "2026-03-01"}` | false |
| `startDate NOT BETWEEN [...]` | `{startDate: null}` | **true** |

The first row is the one that bites a form: on a blank create screen every date condition must be
false, or the form refuses itself before the user has typed anything.

### Values coerce by the declared type

Not by the shape the value happens to have.

| Condition | Field type | Row | Expected |
|---|---|---|---|
| `code = "7"` | String | `{code: "007"}` | **false** |
| `amount = 10` | BigDecimal | `{amount: "10.00"}` | true |
| `expiryDate < "{{ NOW }}"` | Date | `{expiryDate: today}` | **false** |
| `at < "{{ NOW }}"` | DateTime | `{at: "today 09:30"}` | true |
| `startTime = "09:00:00"` | Time | `{startTime: "09:00:00.500"}` | **false** |
| `isPrimary = true` | Boolean | `{isPrimary: 1}` | true |
| `managerId > 100` | ManyToOne | `{managerId: 42}` | **true** |

Four traps in one table. A String field holding a zero-padded code is not a number. A **Date** holds
no time, so it is truncated to the day before comparing — a field holding today is not "before now"
because the clock has moved past midnight. A **Time** keeps its fraction: `09:00:00.500` is not
`09:00:00`. And a relation compares as **text**, because the evaluator's default kind is text — `42`
sorts after `100`.

### A multi-value field is a set

| Condition | Row | Expected |
|---|---|---|
| `tags = "a"` | `{tags: ["a","b"]}` | true |
| `tags IN ["c","b"]` | `{tags: ["a","b"]}` | true |
| `tags IN ["c"]` | `{tags: ["a","b"]}` | false |

### Placeholders and reserved variables

| Condition | Note |
|---|---|
| `endDate < "{{ @startDate }}"` | another field of the same row |
| `dateOfBirth > "{{ TODAY - P13Y }}"` | environment token with an ISO-8601 offset |
| `@mode = "update"` | the write's mode, read from the context, not the row |
| `@userId = 42` | the signed-in user, likewise |

`TODAY` / `YESTERDAY` / `NOW` resolve on the server's clock here and on the browser's clock in a form.
The corpus pins them by **supplying the instant** in the case rather than reading a real clock, so it
tests the arithmetic, not the timezone. The timezone difference is a known open question and is not
something the corpus can settle.

### Spelling

| Spelling | Status |
|---|---|
| `reason = "Others"` in a text block | the form to write |
| `[["reason", "=", "Others"]]` | parses to the same tree |
| `costCentreId IS NOT SET` as an expression | **refused** — valueless operators have no expression form |
| `[["costCentreId", "IS NOT SET", null]]` | how to write those: three elements, the third ignored |

## Beyond the evaluator

Three rules live in `FieldConstraintsEnforcer` rather than in the expression, and a client that
renders a form has to mirror them too. They take a write mode, so their cases carry one.

| Rule | Create | Update |
|---|---|---|
| a hidden field (`hidden` or a matching `hiddenWhen`) | not judged at all | not judged at all |
| `requiredWhen = "true"` | required | fires **only when the write names the field** — may omit, may not clear |
| any conditional rule | evaluated | evaluated only when the patch touches the field or something it reads |
| `readonlyWhen` | rejects a non-null value | rejects an **assignment**: the patch names the field and the value differs from the stored one |
| value domain (`min` / `max` / `pattern`) | empty passes; checked after coercion; a pattern matches the whole trimmed value | same |

The `requiredWhen = "true"` row is the one worth re-reading. It is what lets a nullable column carry
an application-level requirement: a row written before the rule existed stays editable, because an
edit that does not mention the field is not a violation. A client that renders it as a plain required
field makes those rows unsaveable.

## Adding a case

Add it when a defect is found in any implementation — the case is the regression test, and it is
worth more in the corpus than in one codebase's test file, because it then constrains every
implementation. Name the case after the rule it protects, not after the bug.
